# Aegis — Implementation Plan

Six phases. Each has concrete deliverables and acceptance criteria that are pass/fail, not subjective. A phase is complete only when every criterion passes on Coston2 against the live chain, not in a local simulation.

---

## Phase 0 — Unblock the critical path

Everything else waits on two external dependencies. Start these before writing any code.

### Deliverables

1. **Coston2 indexer credentials requested.** The `ext-proxy` queries Flare's C-chain indexer to find TEE instruction events and cannot start without database access. Request through Flare technical support or `@FlareDevs`, stating what is being built. The Coston2 indexer is reachable without a VPN at `34.38.42.208:3306`, database `indexer`. Coston uses different credentials and requires a VPN — use Coston2.
2. **Coston2 wallet funded** from the faucet, with enough C2FLR for gas, extension registration, and per-instruction fees.
3. **Scaffold running unmodified.** Clone `flare-foundation/fce-extension-scaffold`, run the Hello World `SAY_HELLO` and `SAY_GOODBYE` end-to-end against Coston2 with `SIMULATED_TEE=true`. Do not touch a line of Aegis code until this passes.
4. **Reserved tunnel domain.** ngrok free tier gives one reserved domain that survives restarts; cloudflared quick tunnels generate a new URL every run and force `EXT_PROXY_URL` edits and re-registration each time. Use ngrok.

### Acceptance

- `./scripts/test.sh` on the untouched scaffold passes against Coston2.
- `curl -s "$EXT_PROXY_URL/info" | jq '.machineData'` shows a code hash starting `0x194844cf`, the extension id from `config/extension.env`, and your address as `initialOwner`.

### Why this is phase 0

Registering a TEE machine touches attestation, the FDC relay path, the signing policy, and an indexer you do not control. Every failure mode here — `InvalidGovernanceHash`, `ChallengeExpired`, `code hashes do not match`, proxy never becoming ready — is environmental. Discovering them while also debugging your own XRPL serialiser is the single most likely way this project fails.

## Phase 1 — Policy layer in Solidity

No TEE involvement. Pure contract work, fast iteration under `forge test`.

### Deliverables

1. `PolicyEngine.sol` — policy creation, immutable versions, tier resolution, allowlist, role bitmasks.
2. `TreasuryRegistry.sol` — treasury creation, freeze, sequence tracking. `bindXrplAccount` written but not yet reachable.
3. `PaymentController.sol` — the full state machine: propose, approve, dispatch guard, rolling window accounting with lazy pruning.
4. FTSO integration — derived feed id, staleness check, drops-to-USD conversion.
5. Complete test suite for every rule.

### Acceptance

Each of these is an individual passing test:

- Tier resolution returns the correct tier at, just below, and just above every ceiling.
- A payment above the highest ceiling reverts `AmountExceedsPolicyCap` at proposal.
- Rolling window exhaustion blocks a dispatch that passed at proposal.
- Non-allowlisted destination reverts. Destination tag `0` correctly means "any tag".
- Proposer cannot approve their own request.
- The same address cannot approve twice.
- Dispatch before `eligibleAt` reverts.
- A price older than 180 seconds reverts dispatch.
- A frozen treasury rejects propose, approve, and dispatch.
- Policy amendment requires the amendment threshold and timelock.

### Notes

Write `PaymentController.dispatch` to re-run the entire policy check rather than trusting the proposal-time result. The price moves and the window is shared. A request that was valid an hour ago is not automatically valid now, and grandfathering is how treasuries get drained.

## Phase 2 — XRPL serialiser and signer in Go

Still no TEE. A standalone Go package, tested against known-good vectors.

### Deliverables

1. `internal/xrpl/serialize.go` — canonical field serialisation sorted by `(typeCode, fieldCode)`, covering `TransactionType`, `Flags`, `Sequence`, `DestinationTag`, `LastLedgerSequence`, `Amount`, `Fee`, `SigningPubKey`, `TxnSignature`, `Account`, `Destination`, `Memos`.
2. `internal/xrpl/address.go` — AccountID derivation and base58check classic address encoding with the XRPL alphabet.
3. `internal/xrpl/sign.go` — SHA-512Half with the `0x53545800` prefix, RFC 6979 deterministic ECDSA, DER encoding with low-S, transaction id with the `0x54584E00` prefix.
4. Test vectors taken from the XRPL reference implementation, not generated by this code.

### Acceptance

- Serialising a known transaction produces byte-identical output to the reference vector.
- A known keypair and transaction produce the reference signature exactly.
- A known public key derives the reference classic address.
- Omitting a zero `DestinationTag` produces a different hash than including it, and the omitting path is the one used.
- Signing the same request twice produces identical bytes, confirming RFC 6979.

### Notes

Do not pull in an XRPL library. The enclave image is the unit of attestation and must stay small and reproducible. This package is a few hundred lines and testable in isolation, which is worth far more than a dependency.

## Phase 3 — TEE extension

Now connect phases 1 and 2 through FCC.

### Deliverables

1. `AegisInstructionSender.sol` — `XRPLW` op type with `KEYGEN`, `SIGNTX`, `STATUS` commands, built on the scaffold's untouched constructor and `setExtensionId()`.
2. `internal/config/config.go` — the three constants and `Version`.
3. `pkg/types/types.go` — `SignRequest`, `SignResponse`, `KeygenResponse`, `State`.
4. `pkg/types/register.go` — ABI decoder registrations for every message and result pair.
5. `internal/extension/extension.go` — routing on `opType`, sub-routing on `opCommand`, three handlers.
6. **The digest check.** `processSignTx` recomputes `keccak256` over the decoded fields and compares against `policyDigest` before touching the key.
7. Key generation in-enclave with `crypto/rand`, stored under mutex, never logged or returned.
8. `GET /state` returning `hasKey` booleans and last-signed sequences only.
9. `TreasuryRegistry.bindXrplAccount` wired to the `KEYGEN` result, with on-chain AccountID derivation using precompiles `0x02` and `0x03`.

### Acceptance

- `KEYGEN` produces an XRPL address, binds it on-chain, and a second binding attempt reverts.
- The on-chain derived AccountID matches the address returned by the enclave.
- `SIGNTX` with a correct digest returns a valid signed blob whose signature verifies against the treasury public key.
- `SIGNTX` with any single field altered returns status `0` and the log `policy digest mismatch`, with no signature produced. Test this by tampering with a real payload, not by constructing a fake one.
- `GET /state` contains no key material under any input.
- A full propose → approve → dispatch → signature cycle completes on Coston2.

### Notes

The three-way constant alignment is the most common failure here. When you see `unsupported op type`, check `bytes32("XRPLW")` against `OPTypeXRPL` against `teeutils.ToHash(config.OPTypeXRPL)` before debugging anything else.

Keys are generated in the enclave, never imported. The scaffold's ECIES `/decrypt` path on port 7701 exists and is documented, but sending an encrypted key through calldata means putting it in permanent public storage, and encryption breaks over time. Import is phase 5 and travels off-chain.

## Phase 4 — Settlement and proof

Close the loop. This is what separates Aegis from a signing service.

### Deliverables

1. `submitter/src/watcher.ts` — websocket subscription to `PaymentSigned` on Coston2.
2. `submitter/src/xrpl.ts` — submit to XRPL Testnet at `wss://s.altnet.rippletest.net:51233`, poll `tx` until `validated: true` or `LastLedgerSequence` passes.
3. `submitter/src/fdc.ts` — request a `Payment` attestation with `sourceId = testXRP`, wait for round finality, retrieve the Merkle proof from the DA layer.
4. `ExecutionVerifier.sol` — `confirmSettlement` verifying source, destination, amount, and the memo reference against `keccak256(abi.encode(requestId))`; `confirmNonExecution` consuming a `ReferencedPaymentNonexistence` proof.
5. Window spend release and sequence advance on the failure path.

### Acceptance

- A payment settles on XRPL Testnet and the FDC proof moves the on-chain state to `Settled`.
- A proof for a different transaction is rejected by `confirmSettlement`.
- A transaction deliberately allowed to expire past `LastLedgerSequence` is proven non-existent, moves to `Failed`, releases the committed window spend, and advances the sequence so the next payment is not wedged.
- The submitter holds no authority: manually calling `confirmSettlement` with a fabricated proof reverts.
- Running two submitters simultaneously causes no double-spend and no state corruption.

### Notes

The sequence advance on the failure path is easy to skip and catastrophic to omit. Without it, one expired transaction blocks the treasury permanently, because XRPL will keep expecting that sequence number.

## Phase 5 — Interface and hardening

### Deliverables

1. Dashboard: treasury overview, policy authoring, proposal creation with live policy validation before submission, approval screen showing every fact the contract checks, audit log linking Coston2 and XRPL transactions.
2. Countdown timers for timelocks and a live rolling-window gauge.
3. Guardian freeze as a one-click action with confirmation.
4. Error surfacing that maps every custom Solidity error to a plain-language explanation of which rule blocked the payment.
5. README with a from-zero setup path.
6. Demo video, 90 seconds, showing a policy-compliant payment settling and a policy-violating payment being refused.

### Acceptance

- A person who has not seen the codebase can create a treasury, define a policy, propose a payment, approve it with a second account, and watch it settle, using only the README.
- Every rejection in the UI names the rule that fired.
- The audit log for any request can be reconstructed independently from chain data with no Aegis service running.

### Notes

The approval screen is the product's most important surface. An approver who cannot see the destination, tag, both amounts, tier, threshold, and unlock time is approving a description rather than a fact, which is the exact failure Aegis exists to prevent.

## Phase 6 — Multisig and PMW migration

Post-hackathon, specified now because the architecture depends on it being possible.

### Deliverables

1. k-of-n signing across TEE machines, with `getRandomTeeIds(extensionId, n)` returning multiple machines.
2. XRPL `SignerList` configured with the n enclave-held keys.
3. Multi-sign serialisation: hash prefix `0x534D5400` with the signer's AccountID appended, per-signer `Signers` array entries.
4. Migration of `AegisInstructionSender.requestSignature` to call PMW instead of the custom extension when its interface becomes public.
5. Key import path over an off-chain channel to the proxy, for existing treasuries.

### Why the architecture already supports this

`requestSignature` is the only function in the system that touches signing. Everything in `PolicyEngine`, `TreasuryRegistry`, and `PaymentController` is signing-agnostic. `SignRequest` deliberately carries structured fields rather than a serialised blob, so a different signer consuming the same fields is a drop-in replacement.

PMW provides natively what phase 6 builds by hand: wallets as sets of keys across TEE machines acting as k-of-n signers on native XRPL and BTC multisig accounts, per-instruction nonces with transaction chaining on UTXO chains, reissuance at a different fee, nullification by consuming a nonce with a minimal-fee transaction, and FDC execution proofs. Building the custom extension first is not wasted work — it is what makes the migration a module swap rather than a rewrite, and it is the only route available while system extension ids below `0x10000` remain reserved.

## Risk register

| Risk | Impact | Mitigation |
|---|---|---|
| Indexer credentials delayed | Total block — the proxy cannot start | Requested in phase 0, before any code. Phases 1 and 2 are fully independent of the TEE and proceed in parallel while waiting |
| FCC is not a fully public production system | API changes mid-build | Pin the scaffold commit. Keep all FCC contact surface inside `AegisInstructionSender.sol` and `internal/extension/`. Bump `Version` on every behaviour change |
| XRPL serialisation subtly wrong | Signatures rejected, wasted debugging | Phase 2 is standalone and validated against reference vectors before touching the enclave |
| System contract addresses move to `FlareContractRegistry` | Deploy config breaks | Addresses read from `config/coston2/deployed-addresses.json` in one place; the migration is a one-line change |
| Attestation and registration failures | Days lost | Every known failure mode and its fix is catalogued in `DOCS.md` §7 |
| Single TEE machine holds the key | Machine loss means treasury loss | Stated openly as a v1 limitation. Phase 6 removes it. Never claimed otherwise in the submission |
| FTSO staleness blocks demo | Demo failure at the worst moment | Rehearse. If the feed is stale during a live demo, that is the fail-closed design working, and saying so is a stronger answer than a fallback price would be |
| Scope creep into BTC or issued currencies | Nothing finishes well | Explicitly out of scope in `PRD.md` §6. Roadmap material only |

## Sequencing

Phases 1 and 2 are independent of each other and of phase 0's external dependency. Run all three concurrently from day one. Phase 3 requires all of 0, 1, and 2. Phase 4 requires 3. Phase 5 requires 4. Phase 6 is post-program.

The dependency that determines the schedule is the indexer credentials. Request them first, then build the two halves that do not need them.

---

## Definition of done

The project is done when a person outside the team can, using only the README:

1. Create a treasury whose XRPL key was born inside a TEE.
2. Define a policy with tiers, a rolling window, and an allowlist.
3. Propose a payment, have a second account approve it, wait out the timelock, and watch it settle on XRPL Testnet.
4. See the settlement confirmed on Coston2 by an FDC proof.
5. Attempt a payment that violates each rule and be refused each time, with the specific rule named.
6. Reconstruct the entire history from chain data alone, with no Aegis service running.
